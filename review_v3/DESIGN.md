# 复核引擎 v3 设计说明

API 与批量复核共用的同一个复核引擎。入口：`review_v3.engine.run_review()`，
返回值与旧版 `api.services.review.run_review_single()` 完全一致，PDF 渲染、
发布校验与数据库写回沿用原有共享实现。

## 为什么重写

2026-10 实测（242 个 API 会话、约 7200 个批量会话）：

- 会话墙钟 89% 是模型推理，工具执行仅 11%；单轮延迟随上下文增长（2–4 万 token 约 3 s，8 万以上约 8 s）。
- 约一半轮次在做机械取数（重抽 PDF 文本、渲染裁图、浏览文件），且 r1 / r2 / judge 各重复一遍。
- 固定轮数几乎都被触顶（首轮 64%，反证核验 98%，综合判定 95%），与该论文必查项的数量无关。
- 低风险论文最贵：两次完整调查串行。

## 流程

1. **证据包**（确定性，复用原 `review_evidence.py` 及其补充扫描）：必查清单 `must_address`、HIGH 发现、源数据扫描。
2. **论文资料包**（确定性，新）：逐页正文、图表/表格图注索引、参考文献段、源数据清单、图像告警清单；
   按需渲染与裁剪图片（缩放后供模型查看），全部有缓存。
3. **核查清单分片**：必查项按维度（图像 / 数据 / 图文一致性 / 参考文献 / 研究设计）分组，
   数据和图文一致性按数量拆分成多个分片。每个分片一个台账文件。
4. **并行调查**：每个分片一个模型会话（MiniMax-M3.1-Flash，settings-mm.json），只带本分片的规则、
   清单、相关 memory 判据和资料包工具。调查结论逐项写入台账。
5. **按进展分配预算**：每次运行一个轮数块；台账有新关闭项就继续追加，连续无进展即停止。
   不设与论文无关的固定总轮数，整篇墙钟上限仍保留。
6. **逐分片反证核验**：新会话独立复查——确认问题是否真实（防误报）、排除理由是否站得住（防漏报），
   并可补充新问题。分片调查一结束就开始核验（流水线）。
7. **分歧仲裁**：只对两方结论不一致的条目开定向会话。
8. **定稿**：风险结论由台账确定性给出（任一维度存在已确认的实质问题即“有风险”）；
   写作会话不带工具，只把已核实事实写成报告 JSON。截图与问题编号由台账确定性绑定。
   一个问题同时涉及论文页面和随文源数据时，两侧都必须有截图；截图会话没补齐的一侧由
   `review_v3/autocrop.py` 补截（表格截到最后一行，源数据按引用数值定位单元格）。
9. **发布校验**：与渲染器共用 `api.services.review_validation.validate`；
   不通过时先做纯写作修复，缺事实再对缺口条目做定向补查。

所有阶段都有检查点：台账和阶段状态落盘，进程重启后已完成的分片直接复用，
进行中的分片以台账为准继续，不会重置预算、不会重做已完成的核查。

## memory 与 skill

- 规则：`review_v3/rules/*.md`，由 `RUNTIME_RULES.md`、旧版提示词与 `AGENTS.md` 交付规范提炼，按维度拆分，受版本管理。
- memory：`review_v3/memory.py` 为审计 memory 建立 BM25 索引。每个分片按告警类型、表头、图注关键词检索相关判据注入提示词；
  会话中也可用 `pv3 mem` 按需检索。核验推翻调查结论的条目写入 `memory_inbox/` 供人工整理，不自动写回 memory。

## 与旧版的切换

- API：`REVIEW_ENGINE=v3` 时 `run_review_single` 转交 v3（需重启服务后生效）；改为 `v2` 并重启即回退。2026-11-04 起线上 API 已启用 v3，配置见 `deployment/paper-api-review-engine.conf`。
- 批量：`python -m review_v3.batch` 通用批量入口，按表名/条件取论文，替代按批次复制的 r1/r2/judge 守护脚本。
